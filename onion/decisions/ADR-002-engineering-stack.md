# ADR-002 — Canonical Onion engineering stack

**Status:** Accepted (Founder decision DR-02 option A with database refinement, 2026-10-03)  
**Decider:** Uday Teki  
**Spike evidence:** throwaway spike run outside the repository on 2026-10-03 (see §Evidence); no spike code was committed.

## Decision

| Layer | Choice | Rules |
|---|---|---|
| Language | **TypeScript end-to-end** | one language for UI, commands, agent runtime, tests |
| Framework | **Next.js App Router** | Server Components and server-side boundaries by default; client components only where interaction requires; no forcing everything into client-side React |
| UI | React + TypeScript; **Onion-specific design system** (`UI_UX_SYSTEM.md`) | dense operational workflows, accessibility, responsive, evidence/approval/risk/status, human–AI distinction |
| Database dialect | **PostgreSQL from day one** | no SQLite anywhere in the canonical path. **Founder correction accepted:** Drizzle schemas are dialect-specific (`drizzle-orm/pg-core` vs `sqlite-core` column types, defaults, enums, JSON, triggers); there is no single table definition that runs unchanged on both. Cursor's earlier "embedded SQLite now, PostgreSQL unchanged later" framing in DR-02 option A is **retracted**. |
| ORM / migrations | **Drizzle ORM + Drizzle Kit** | schema in TypeScript; generated SQL migrations committed; **no production schema mutation outside the migration process**; Better Auth tables generated by `@better-auth/cli generate` into the same Drizzle schema so one migration process owns all tables |
| Dev / test / early-pilot DB | **PGlite** (embedded PostgreSQL) | local development, automated tests, early single-user/controlled pilot where appropriate |
| Shared / staging / production DB | **PostgreSQL** | provider is a deployment decision after the private repository and deployment account exist; **domain layer must not couple to a managed-Postgres vendor** (no vendor SDKs in domain modules; connection via standard `pg`/`postgres` driver behind one adapter) |
| Authentication | **Better Auth + Google Workspace sign-in** | login restricted to Uday's authorized Workspace domain/account policy. Mechanism verified in `@better-auth/core@1.7.7` `social-providers/google`: the `hd` option is sent as the Google authorization hint **and** enforced against the verified `hd` claim of the returned ID token (`verifyClaims`), rejecting sign-in on mismatch or missing claim. Onion sets `hd: "<practice domain>"` and additionally applies an application-side account allowlist/role check in a `databaseHooks.user.create.before` hook so that a valid Workspace identity still receives **no authority** until provisioned. `emailAndPassword` disabled. |
| Authorization | **application-controlled**, separate from authentication | verbs VIEW · COMMENT · CONTRIBUTE · MANAGE · APPROVE · DELEGATE · ADMINISTER modelled explicitly; deterministic policy function with exhaustive tests; sign-in grants no authority by itself |
| Google APIs | identity only (`openid email profile`) | additional scopes added capability-by-capability under least privilege with explicit approval; never request Gmail/Drive/Calendar scopes because sign-in exists |
| AI | **model/provider-neutral Agent Control Plane** (`AI_CAPABILITY_ARCHITECTURE.md`) | OpenAI may power initial capabilities; business roles (ATLAS/RAS/GROWTH/DELIVERY) never equal a provider or model; fixture provider for tests/evals |
| Initial capabilities | ATLAS Executive Briefing · Lead Qualification (A2) · RAS Evidence/Quality | Meeting Intelligence and Research wait for Google-data-scope and web-egress approvals |
| Agent presentation | named actors on records, evidence, recommendations, proposed actions, approvals | no generic chat first; every consequential result exposes agent, objective, evidence/source, analysis vs fact, assumptions, proposed action, approval requirement, execution status, human approver |

## Evidence (spike, 2026-10-03, Node v22.14.0, Linux x86_64, outside repo)

Versions installed from the npm registry: `next@16.3.8`, `react@19.3.0`, `react-dom@19.3.0`, `drizzle-orm@0.45.3`, `drizzle-kit@0.31.11`, `@electric-sql/pglite@0.5.8` (reports `PostgreSQL 18.3`), `better-auth@1.7.7`, `zod@4.6.5`, `typescript@7.0.2`, `tsx@4.23.15`.

| Check | Result |
|---|---|
| `drizzle-kit generate` with `dialect: "postgresql"` from a TypeScript schema (audit_event + Better Auth tables) | migration SQL generated |
| `drizzle-orm/pglite/migrator` applies the committed migration to an in-memory PGlite | applied |
| Append-only `audit_event` enforced with a PostgreSQL `BEFORE UPDATE OR DELETE` trigger raising an exception | UPDATE blocked, DELETE blocked (PostgreSQL semantics unavailable in SQLite — the reason for the PGlite refinement) |
| Idempotency: duplicate `operation_key` insert | rejected by unique constraint |
| Better Auth with `drizzleAdapter(db, { provider: "pg" })` on the same PGlite instance, Google as the only social provider, email/password disabled | initialises; `getSession` without cookie → `null`; adapter creates a user into the Drizzle-managed `user` table |
| Better Auth schema generated via `npx @better-auth/cli generate` | required — a hand-written schema had the wrong `emailVerified` type; CLI output is the source of truth |
| Next.js App Router Server Component querying PGlite under `next build` + `next start` | renders; audit count increments across requests; requires `serverExternalPackages: ["@electric-sql/pglite"]` in `next.config.ts` |
| Drizzle error wrapping | driver errors surface in `error.cause`; application error handling must inspect the cause chain |

Known limitation of the spike: Google sign-in flow was not exercised (no OAuth client exists yet — needs a practice-owned Google Cloud project); PGlite persistence to disk and backup/restore were not exercised (Sprint 0 items 5 and 12).

## Consequences

- Sprint 0 items 1–15 (`SPRINT_1_PROPOSAL.md` §1) are implemented against this stack in the private repository.
- `ARCHITECTURE_CURRENT.md` §9–§11 updated to match (PGlite instead of generic embedded store; Better Auth instead of Auth.js).
- An `adapter` seam isolates the database driver (PGlite in dev/test/early pilot; `pg` for hosted PostgreSQL) so switching is configuration, not code.

## Reversibility

Framework/language: medium (rewrite of the slice). Database host: high by design. Auth library: medium (session/table shape), mitigated by Drizzle-owned schema.
